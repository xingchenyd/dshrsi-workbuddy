# 本地受控效果对照

这里回答一个具体问题：**同一组重复错误请求，在打开 WorkBuddy RSI 后，哪些会在执行前被拦下，正常检查是否仍能执行？**

[results.json](results.json) 是脚本实际运行生成的完整记录，包含环境、时间、工作负载、每次请求的结果与统计。错误来自操作系统真实的 `ENOENT`，正常命令也由本机 Node 实际执行。本对照调用 WorkBuddy 适配器及其 RSI 引擎，不调用模型，不连接 WorkBuddy 桌面会话。

## 结果

本次环境：Windows x64、Node.js v22.17.0。记录的 UTC 时间见 JSON 的 `generatedAt`。开关两组均从独立、空白的临时状态目录开始；OFF 使用适配器真实的关闭开关。

| 固定工作负载 | OFF | ON | 本次观察 |
| --- | ---: | ---: | --- |
| 冷启动：12 次相同缺失命令请求，实际触发 ENOENT 的次数 | 12 | 5 | 7 次请求在执行前被拒绝 |
| 冷启动：4 次穿插的正常 `node --version` | 4/4 成功 | 4/4 成功 | 正常请求未被拦截 |
| 重开 host：6 次相同缺失命令请求，实际触发 ENOENT 的次数 | 6 | 3 | 3 次请求在执行前被拒绝 |
| 重开 host：2 次穿插的正常 `node --version` | 2/2 成功 | 2/2 成功 | 正常请求未被拦截 |
| 写入代码后，尚未验证时请求 Stop | 允许结束 | 要求验证 | ON 能提示补充验证步骤 |
| 实际执行 `node --check example.mjs` | 1/1 成功 | 1/1 成功 | 两组均运行相同语法检查 |
| 语法检查成功后请求 Stop | 允许结束 | 允许结束 | 验证完成后可结束当前回合 |

“失败启动”指向操作系统请求启动一个不存在的可执行文件、得到 `ENOENT`。这个文件并没有成功启动。ON 中的拒绝发生在请求启动之前，不能把它算成已经执行的命令。

重开 host 场景另有**每组 2 次真实失败的学习阶段**，JSON 中保存在 `restartAndReuse.*.training`，不包含在表中后续 6 次请求内。如果统计这个场景的全部失败成本，OFF 为 **2 + 6 = 8** 次，ON 为 **2 + 3 = 5** 次。ON 在关闭前与重开后都保存了 1 条适应规则，新会话收到包含该缺失命令名称的上下文。这里的“重开”是销毁并重新创建适配器 host 对象、重新读取磁盘库，未重启操作系统进程或 WorkBuddy 桌面应用。

## 复现

在项目根目录执行，无须模型 API Key，也无须安装额外依赖：

```bash
node scripts/benchmark-workbuddy.mjs
```

将这次运行保存为可审查的 JSON：

```bash
node scripts/benchmark-workbuddy.mjs --output docs/workbuddy/benchmarks/results.json
```

运行相应回归测试：

```bash
node --test test/workbuddy/benchmark.test.mjs
```

脚本只在 `mkdtemp` 创建的专属临时目录内写入测试文件和学习库，并在结束时清理这个目录。显式指定 `--output` 时才写入结果文件。测试使用同一个真实运行入口，检查工作负载数量、错误来源、拦截计数、正常命令、持久化上下文和 Stop 行为；策略变化导致结果改变时，测试会提醒重新审阅并更新公开证据。

## 方法与解释

1. **相同请求，真实错误。** 两组都按同一顺序尝试专为本测试命名的缺失程序 `wbrsi_benchmark_missing_8c96d --version`。脚本以 `spawn(..., { shell: false })` 请求操作系统执行，并要求实际返回 `ENOENT`；若程序意外存在，测试直接失败，不会伪造错误。每 3 次缺失请求后安排一次正常检查。
2. **固定驱动，独立状态。** 驱动刻意不采纳注入的自然语言建议，继续发送同一工作负载，只有真实 `PreToolUse` 决策可以阻止进程启动。这隔离了工具拦截机制的作用，不代表一个模型一定会这样重试。适配器使用默认 `synth` 生成器，模型调用数为 0。
3. **保留探测性重试。** 引擎会允许部分后续请求探测“先前的拒绝是否仍合理”。这些请求确实尝试启动程序，失败也完整计入 ON 的统计；没有把它们从结果中扣除。
4. **新会话读取已有规则。** 重开场景独立进行：每组先运行 2 次真实失败，再关闭 host、重新打开同一磁盘学习库，随后开始新的会话。`startupContext` 仅在返回的上下文确实包含测试缺失命令名称时为 `true`。长时间继续失败可能使规则修订为直接拒绝，届时未必还有提示文本，因此这里只描述这组学习路径。
5. **结束前验证。** 脚本真实写入 `example.mjs` 并发送对应 Write 工具事件，立即请求 Stop；随后两组都实际执行 `node --check`，再次请求 Stop。OFF 在第一次已允许结束，因此脚本在新回合安排同样的检查。它测量的是“是否要求验证”和验证后的结束行为；语法检查不能证明任意代码在功能上正确。
6. **可核对的轨迹。** JSON 的 `trace` 保留每次请求是否通过、被拒绝、实际成功或失败，以及操作系统错误码；图表应直接使用 `scenarios.*` 的计数。`observedValidationStages` 列出这次生成规则所经过的五类校验阶段：static、load、rehearsal、regression、policy。

## 证据边界

这是小规模、预先固定工作负载下的**机制对照**。它证明在这些用例里，适配器能够减少真实失败的启动尝试、保留正常请求、读取持久规则，并要求补充验证。Hook 以 WorkBuddy 形状的输入在进程内调用，未经过 daemon 网络传输或 WorkBuddy 桌面应用。

没有测量真实模型的任务完成率、Token 节省、端到端耗时或用户生产力；没有运行多模型、多项目的统计实验。本页数字不能转述成“模型成功率提升”“开发效率提升”或通用的错误下降比例。其他命令、错误类型、任务分布和规则状态需要另行测试。适配器协议、daemon、安装器等回归检查由项目的其他测试覆盖，应与这里的作用对照分别阅读。
